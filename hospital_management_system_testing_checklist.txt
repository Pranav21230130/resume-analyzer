HOSPITAL MANAGEMENT SYSTEM COMPLETE TESTING CHECKLIST
========================================

Project Technology: - React + Vite frontend - Express.js backend -
SQLite database

Purpose: Use this checklist to test the Hospital Management System. Mark
each item PASS, FAIL, BLOCKED, or NOT TESTED after actually performing
the test. This checklist does not mean the tests have already passed.

1.  APPLICATION STARTUP [ ] Frontend starts at http://localhost:5173/ [
    ] Backend starts at http://localhost:5000/ [ ] No startup errors
    appear in the terminal [ ] Production build completes successfully [
    ] Frontend can communicate with the backend [ ] Backend connection
    failures are handled with a clear message [ ] Browser console and
    server logs contain no unresolved critical errors

2.  LOGIN, AUTHENTICATION, AND AUTHORIZATION [ ] Valid admin credentials
    allow login [ ] Invalid passwords are rejected [ ] Unknown email
    addresses are rejected without revealing sensitive account details [
    ] Logout invalidates the session or token [ ] Protected API routes
    reject unauthenticated requests [ ] Direct navigation does not
    bypass access restrictions [ ] Each role can access only its
    permitted features [ ] Expired sessions or tokens are rejected [ ]
    Repeated failed login attempts are rate-limited [ ] Passwords are
    stored using a strong password-hashing algorithm [ ] Inactive
    accounts cannot log in [ ] Users cannot change their role by editing
    frontend data or API requests

3.  DASHBOARD AND NAVIGATION [ ] Dashboard loads without critical errors
    [ ] Dashboard counts match database records [ ] Empty data sets
    display suitable empty states [ ] Loading indicators appear while
    data is being retrieved [ ] API failures display understandable
    error messages [ ] Navigation links open the correct modules [ ]
    Dashboard data refreshes after relevant changes

4.  PATIENT MANAGEMENT [ ] Register a patient with valid details [ ]
    Required fields reject missing or whitespace-only values [ ] Invalid
    dates, ages, phone numbers, and email addresses are rejected [ ]
    Duplicate patient identifiers are prevented [ ] Search by patient ID
    and name works [ ] Editing a patient saves the correct values [ ]
    Patient details display the correct associated records [ ] Deletion
    or archival follows the hospital’s retention rules [ ] Patient
    records remain available after a backend restart [ ] Unauthorized
    users cannot read or modify restricted patient records

5.  DOCTOR MANAGEMENT [ ] Create a doctor with valid details [ ]
    Required fields and unique doctor identifiers are enforced [ ]
    Specialty and department assignments are valid [ ] Edit, view, and
    search doctor records [ ] Deactivate a doctor safely [ ] Inactive
    doctors cannot receive new appointments [ ] Doctor schedules reject
    invalid time ranges [ ] Existing historical appointments remain
    correctly linked to doctors [ ] Only authorized users can modify
    doctor records

6.  DEPARTMENT MANAGEMENT [ ] Create, view, edit, and search departments
    [ ] Duplicate department codes are prevented [ ] Department
    assignments are valid [ ] Department counts match assigned doctors
    and staff [ ] Departments with linked records cannot be deleted
    unsafely [ ] Invalid department references are rejected [ ] Only
    authorized users can change department information

7.  APPOINTMENT MANAGEMENT [ ] Book an appointment for an existing
    patient and doctor [ ] Invalid dates and times are rejected [ ]
    Doctor availability and working hours are checked [ ] Conflicting
    bookings are rejected when double-booking is prohibited [ ]
    Rescheduling saves the correct date and time [ ] Cancellation
    updates the appointment status correctly [ ] Invalid status
    transitions are prevented [ ] Simultaneous booking requests are
    handled safely [ ] Duplicate submissions do not create duplicate
    appointments [ ] Search and filtering by patient, doctor, date, and
    status work [ ] Appointment changes persist after a backend restart

8.  ADMISSIONS, BEDS, AND WARDS [ ] Admit an existing patient [ ] Assign
    an available bed and ward [ ] Prevent two active admissions from
    occupying the same bed [ ] Discharge a patient and release the bed
    correctly [ ] Invalid admission and discharge dates are rejected [ ]
    Ward and bed transfers update availability correctly [ ] Repeated
    discharge requests are handled safely [ ] Failed operations do not
    leave inconsistent bed assignments [ ] Concurrent attempts to
    allocate the same bed are handled safely [ ] Admission history
    remains accurate after discharge

9.  PHARMACY AND INVENTORY [ ] Create and update medicine records [ ]
    Validate medicine name, batch number, expiry date, quantity, and
    price [ ] Negative stock quantities are rejected [ ] Dispensing more
    than available stock is prevented [ ] Expired medicines are flagged
    and handled according to policy [ ] Near-expiry medicines can be
    identified [ ] Stock additions and corrections are recorded
    accurately [ ] Duplicate dispensing submissions do not deduct stock
    twice [ ] Medicine prices and totals are calculated correctly [ ]
    Only authorized staff can change inventory or dispense medicines

10. LABORATORY MANAGEMENT [ ] Create a laboratory order for the correct
    patient [ ] Assign tests and authorized laboratory staff [ ]
    Validate result values and units [ ] Track order, collection,
    processing, and completion statuses [ ] Results remain linked to the
    correct patient and order [ ] Unauthorized users cannot view or
    modify restricted results [ ] Reports display accurate results and
    patient details [ ] Result corrections follow policy and preserve
    appropriate audit history

11. BILLING AND PAYMENTS [ ] Generate a bill for the correct patient or
    encounter [ ] Calculate line items, discounts, taxes, and totals
    correctly [ ] Reject negative or malformed amounts [ ] Record
    partial and full payments accurately [ ] Prevent duplicate payment
    submissions [ ] Calculate outstanding balances correctly [ ] Failed
    payments do not mark bills as paid [ ] Refunds, discounts, and
    payment changes require appropriate permissions [ ] Invoices and
    receipts display correct details [ ] Bill totals, payment records,
    and revenue reports reconcile [ ] Multi-step financial operations
    use database transactions

12. STAFF MANAGEMENT [ ] Create, edit, search, view, and deactivate
    staff records [ ] Validate staff identifiers and contact details [ ]
    Assign roles only to authorized users [ ] Prevent unauthorized
    privilege escalation [ ] Deactivated staff cannot access protected
    features [ ] Personal and employment details are protected [ ]
    Historical records remain linked to the appropriate staff member

13. REPORTS AND ANALYTICS [ ] Report totals match database queries [ ]
    Date ranges and filters work correctly [ ] Sorting and pagination
    work correctly [ ] Revenue calculations follow documented business
    rules [ ] Cancelled or unpaid bills are handled correctly in revenue
    reports [ ] Appointment, admission, laboratory, and inventory counts
    are accurate [ ] Sensitive reports are restricted by role [ ]
    Exports contain the correct rows, columns, dates, and totals [ ]
    Empty and large reports are handled correctly

14. SQLITE AND DATA INTEGRITY [ ] SQLite foreign-key enforcement is
    enabled and verified [ ] User-supplied values use parameterized SQL
    queries [ ] Required fields and unique identifiers are enforced by
    the schema [ ] Foreign-key references are valid [ ] Multi-step
    operations use transactions where necessary [ ] Failed transactions
    roll back without leaving partial changes [ ] Data persists after
    the backend restarts [ ] Concurrent writes and database-lock errors
    are handled safely [ ] Deletion behavior follows foreign-key and
    retention rules [ ] Database files and backups are not publicly
    accessible [ ] A database backup can be restored successfully [ ]
    Test data is kept separate from production data

15. API AND SECURITY [ ] All request bodies, query parameters, and path
    parameters are validated [ ] Every protected API endpoint enforces
    authentication and authorization [ ] SQL injection attempts do not
    execute unintended queries [ ] Untrusted content cannot execute
    scripts in the browser [ ] Users cannot access another patient’s
    records without permission [ ] CORS allows only trusted origins [ ]
    Session cookies or tokens are managed securely [ ] CSRF protection
    is applied to cookie-based authentication where applicable [ ] Error
    responses do not expose secrets, stack traces, or sensitive data [ ]
    Request-size limits and rate limits are configured appropriately [ ]
    Security headers are configured appropriately [ ] Dependencies are
    checked for known vulnerabilities [ ] Production secrets are not
    committed to source control or exposed in frontend bundles [ ] Logs
    avoid unnecessary sensitive patient information

16. USER INTERFACE, ACCESSIBILITY, AND PERFORMANCE [ ] Layout works on
    desktop, tablet, and mobile screens [ ] Keyboard navigation and
    visible focus indicators work [ ] Form fields have accessible labels
    [ ] Color contrast is sufficient [ ] Loading, success, empty, and
    error states are clear [ ] Destructive actions require suitable
    confirmation [ ] Recoverable form errors do not unnecessarily erase
    user input [ ] Date, time, and currency formatting is consistent [ ]
    Large tables and lists remain usable [ ] Critical workflows complete
    without browser console errors

17. AUTOMATED TESTING [ ] Frontend tests use a suitable test framework
    such as Vitest and React Testing Library [ ] Express API tests cover
    success and failure cases [ ] API integration tests use Supertest or
    an equivalent tool [ ] Database tests use a separate test database [
    ] Tests cover invalid inputs and boundary values [ ] Tests cover
    concurrent requests and failure scenarios where relevant [ ] Tests
    do not modify production data [ ] The complete test suite runs after
    fixes [ ] The production build is rerun after fixes [ ] Regression
    tests confirm that existing features still work

18. BUG REPORTING For each failed test, record:

-   Test name
-   Severity: Critical, High, Medium, or Low
-   Affected file, function, API endpoint, or database table
-   Steps to reproduce
-   Expected result
-   Actual result
-   Root cause, if established
-   Fix applied
-   Regression test result

FINAL ACCEPTANCE CRITERIA [ ] All critical and high-severity failures
are fixed [ ] All module workflows have been tested [ ] Authentication
and role permissions have been verified [ ] Patient privacy and database
protections have been checked [ ] Financial calculations and inventory
updates are consistent [ ] Backups and restoration have been tested [ ]
Regression tests pass after fixes [ ] Remaining failures and untested
areas are documented

IMPORTANT This document is a testing checklist, not proof that the
application is error-free. Mark a test as passed only after performing
it and confirming the expected result. Use fictional patient information
during testing. Do not use real patient records in an unsecured demo
environment.
